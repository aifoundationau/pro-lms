2. COMPREHENSIVE ROOT CAUSE ANALYSIS (RCA)
================================================================================

2.1 THE PLATFORM GATEKEEPER TRAP (VERCEL SSO / DEPLOYMENT PROTECTION)
----------------------------------------------------------------------
- Mechanism: Vercel projects configured within teams have an optional feature
  called "Vercel Authentication" or "SSO Deployment Protection".
- Root Cause: In the project settings for `pro-lms` (prj_5X0CXtgppfC1QixUogL2vXnrFD9b),
  the field `ssoProtection` was enabled with mode: "all_except_custom_domains".
- Impact: Because `*.vercel.app` domains are not considered custom domains,
  any non-logged-in visitor requesting preview URLs or direct branch URLs was
  intercepted at Vercel's edge network and redirected to:
  `/_sso-api?url=https%3A%2F%2Fpro-jxjolzgfv-aifoundationau.vercel.app...`
- The user interpreted this third-party login screen as the application's login
  failing, when in reality traffic was prevented from ever reaching the React DOM.

2.2 THE BUILD-TIME ENVIRONMENT VARIABLE INGESTION LIFECYCLE
------------------------------------------------------------
- Mechanism: Vite evaluates `import.meta.env.VITE_*` statically at bundle time
  (`npm run build`). It DOES NOT read environment variables dynamically from
  the browser at runtime unless explicitly injected via `window.__ENV__`.
- Root Cause: Deployment `dpl_23d9fsTKsDyp7R1BceDhCsDA9Maz` had been triggered
  at timestamp 1791618374036, which was BEFORE the 16 environment variables were
  injected into Vercel at timestamp 1791618471996.
- Impact: While the code contained fallback values in `src/firebase.js`,
  production variables on Vercel were out of sync until a fresh deployment was
  built with the new environment variables present during compilation.

2.3 THE OAUTH WHITELISTING TRIAD (FIREBASE AUTH & GOOGLE CLOUD ORIGINS)
-----------------------------------------------------------------------
- Mechanism: Google Identity and Firebase Authentication enforce strict three-way
  origin validation to protect projects against Cross-Site Scripting (XSS) and
  token impersonation:
    1. Firebase Authorized Domains: Whitelists origins allowed to query the
       Firebase Auth iframe/popup handler (`https://<project-id>.firebaseapp.com/__/auth/handler`).
    2. Google Cloud OAuth 2.0 JavaScript Origins: Whitelists hosts that can
       initialize the Google Sign-in flow with Client ID `614773274800-...`.
    3. Google Cloud OAuth 2.0 Redirect URIs: Whitelists destination endpoints
       authorized to receive authorization codes and bearer tokens.
- Root Cause: Vercel URLs (`pro-lms.vercel.app`, `vercel.app`) had not been added
  to the Firebase Console Authorized Domains list. When `signInWithPopup` ran,
  Firebase emitted `auth/unauthorized-domain`.

2.4 FRAGILE CLIENT-SIDE AUTH HANDLERS (THE UNINTENDED REDIRECT LOOP)
--------------------------------------------------------------------
- Mechanism: In `src/services/authService.js`, the catch block for `signInWithPopup`
  contained logic attempting an automatic fallback to `signInWithRedirect`:
    if (error.code === 'auth/popup-closed-by-user' || ...) {
      await signInWithRedirect(...);
    }
- Root Cause: When a user closed the popup intentionally or when an error
  closed the popup, this handler immediately forced the entire browser to
  redirect to Google. If the domain was unauthorized, this created a confusing
  redirection cycle or uninformative white-screen error.
- Impact: User had zero diagnostic feedback explaining what went wrong or how
  to resolve the whitelist restriction.

4. AGNOSTIC AGENTIC INSTRUCTIONS: COMPLETE REPEATABLE ACTION PROTOCOL
================================================================================

Any AI coding agent encountering an OAuth / 3rd-party auth failure on a modern
web deployment MUST execute this standardized 5-phase protocol in order:

--------------------------------------------------------------------------------
PHASE 1: INGESTION & PLATFORM GATEKEEPER AUDIT
--------------------------------------------------------------------------------
1. Test Raw URL Accessibility Before Touching Code:
   Run a headless HTTP request to the target URL:
   `node -e "fetch('<URL>').then(r => console.log(r.status, r.headers.get('content-type')))"`
2. Check for Platform Authentication Interceptions:
   - If the response redirects (301/302/307) to `/_sso-api`, `/login`, or contains
     "Vercel", "Cloudflare Access", or "Basic Auth", the platform is blocking access.
3. Query Platform Project Settings:
   - For Vercel: Query project API / MCP `get_project`.
   - Inspect `ssoProtection`, `passwordProtection`, and `trustedIps`.
   - If enabled on a public application, patch via `update_project` with
     `{ ssoProtection: null }`.

--------------------------------------------------------------------------------
PHASE 2: ENVIRONMENT VARIABLE LIFECYCLE & BUILD SYNCHRONISATION
--------------------------------------------------------------------------------
1. Identify Build Runtime Ingestion Rules:
   - Static frameworks (Vite, CRA): Env vars must exist AT BUILD TIME.
   - Dynamic runtimes (Next.js SSR, Express): Env vars can be read AT RUNTIME.
2. Verify Env Var Creation Timestamps vs Deployment Timestamps:
   - If env vars were added AFTER the last deployment was built, the active
     bundle DOES NOT contain them.
   - Action: Trigger a rebuild or redeployment immediately after updating envs.
3. Ensure Robust Fallbacks in SDK Config:
   - In `src/firebase.js`, provide runtime window injection fallbacks:
     `apiKey: window.__FIREBASE_CONFIG__?.apiKey || import.meta.env.VITE_FIREBASE_API_KEY || "..."`
   - Never allow undefined configs to throw silent initialisation errors.

--------------------------------------------------------------------------------
PHASE 3: IDENTITY PROVIDER (IdP) HOSTNAME WHITELISTING PROTOCOL
--------------------------------------------------------------------------------
1. Collect All Domain Variants:
   - Primary custom domain: `example.com`, `www.example.com`
   - Platform production domain: `project.vercel.app`
   - Platform branch domains: `project-git-main-team.vercel.app`
   - Platform wildcard domain: `vercel.app`
2. Configure Firebase Authentication Whitelist:
   - Route: Firebase Console -> Authentication -> Settings -> Authorized Domains.
   - Add: `<app>.vercel.app` and `vercel.app`.
3. Configure Google Cloud OAuth 2.0 Whitelist:
   - Route: Google Cloud Console -> APIs & Services -> Credentials -> OAuth 2.0 Client IDs.
   - Add Authorised JavaScript Origins:
     - `https://<app>.vercel.app`
     - `https://<project-id>.firebaseapp.com`
   - Add Authorised Redirect URIs:
     - `https://<project-id>.firebaseapp.com/__/auth/handler`

--------------------------------------------------------------------------------
PHASE 4: RESILIENT CLIENT AUTH ARCHITECTURE & ERROR BOUNDARY
--------------------------------------------------------------------------------
1. Separate User Cancellation from System Errors:
   - Do NOT throw errors or initiate fallbacks on `auth/popup-closed-by-user`
     or `auth/cancelled-popup-request`. Return `{ cancelled: true }`.
2. Restrict Fallback to Real Failures:
   - Only fallback to `signInWithRedirect` when popups are genuinely blocked
     (`auth/popup-blocked`, `auth/operation-not-supported-in-this-environment`).
3. Intercept Whitelist Errors with Precision:
   - Catch `auth/unauthorized-domain` and print the exact `window.location.hostname`.
   - Guide the administrator directly to the Firebase Console URL.

--------------------------------------------------------------------------------
PHASE 5: AUTOMATED VERIFICATION & DEPLOYMENT PROMOTION
--------------------------------------------------------------------------------
1. Local Dry Build: Always verify `npm run build` succeeds with zero errors.
2. Push Code: Commit and push changes to the tracking branch.
3. Track Build: Monitor the hosting platform deployment until `READY`.
4. Inspect Live Bundle: Fetch the live script tag and confirm expected hashes.
